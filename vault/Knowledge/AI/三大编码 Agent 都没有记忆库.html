三大编码 Agent 都没有记忆库，只有一堆 Markdown 文件 ​

很多人以为，AI 编程助手"记住你"靠的是一个越来越大的记忆库：聊天越多，向量数据库里塞的东西越多，检索越准。按这个想象，好用的助手应该有一个不断膨胀的私有知识库。

实际拆开三家主流产品的官方文档，结论是反的。

Codex、Claude Code、Cursor 的跨会话记忆，单位都是 Markdown 文件。没有一家在官方文档里描述过用向量库检索记忆。 而且三家的方向一致：常驻的内容越来越小，细节越推越晚，写入端越卡越严。

这不是技术保守，是需求被重新定义了。

一、先看反直觉的部分 ​

最容易误解的是"记忆"这个词。它让人联想到数据库：存进去、按需取、取得到就赢了。但编码 Agent 面对的不是"取不到"，是"取太多"。

一次会话的上下文窗口是有限的。如果每轮都把过去所有会话的摘要灌进去，成本按 token 线性上涨，而且噪声会淹没当前任务。所以你真正要解决的是：在启动时只放极少的一点东西，剩下的等你真的需要时再去拿。

三家的做法不同，但都在回答同一个问题。

CodexClaude CodeCursor
常驻什么记忆摘要 + 合并后的长文MEMORY.md 前 200 行或 25 KB按 frontmatter 条件挂载的规则
细节在哪记忆目录下的其他文件独立主题文件，模型按需打开本地代码索引 + 对话检索
谁写后台抽取模型 + 合并模型会话中模型自写人写规则
自动沉淀有，默认关闭有，本地会话默认开启2.1.x 起移除
向量检索官方文档未描述官方文档未描述官方明确不存代码 embedding

注意最后一列。Cursor 是唯一在文档里明确否认向量检索的一家：Instant Grep 在本机构建并查询索引，不上传路径或代码，也不存代码 embedding。

二、Codex：把会话"编译"成记忆 ​

Codex 的记忆分两层，性质完全不同。

第一层是 AGENTS.md，它是指令链，不是记忆。启动时从全局目录逐级走到当前工作目录，每层取一个文件拼接起来，越靠近 cwd 的越靠后，因此效果上覆盖前面的规则。合并后受 project_doc_max_bytes 限制，默认 32 KiB，超出的部分直接丢弃。

这层的本质是"人写的、进版本控制的约定"。它会被 git 记录，可以 code review，也可以回滚。

第二层才是自动记忆。它把记录拆成两段：先按会话抽取，再跨会话合并，两段可以分别指定模型（extract_model 与 consolidation_model）。产物是 Markdown 文件，下次会话只注入摘要层。

它的门控设计说明了一切：默认关闭；跳过活跃或短命的会话；会话结束不立即处理，空闲 6 小时后才进入候选；剩余额度低于 25% 时跳过后台生成；参与合并的原始记忆默认上限 256 条；30 天未被使用的记忆不再参与合并。

这些规则没有一条在增加记忆，全在限制记忆。

三、Claude Code：索引与数据分离 ​

Claude Code 的核心设计是"索引页 + 数据页"，像数据库。

CLAUDE.md 由人写，放指令；auto memory 由 Claude 自己写，放学到的东西。两者每次会话都加载，但都只是上下文，不是强制配置——官方明确说 CLAUDE.md 作为 user message 放在 system prompt 之后，不保证严格遵从。要强制拦截，得用 hook。

auto memory 只常驻 MEMORY.md 的前 200 行或 25 KB，先到者为准。其余的每条记忆拆成独立主题文件，模型需要时自己打开。启动成本被固定在一个很小的索引上。

真正值得抄的是写入端的减法。官方明确排除两类内容：能从代码库（grep、git）推导的，以及 CLAUDE.md 里已经写过的。 这是索引能长期压在 200 行内的前提。如果不去重，每次会话都在补重复信息，索引很快就会溢出。

还有两个细节：接近上限时提醒压缩，超限写入仍然成功，但下次加载会被截断；写记忆文件时在 frontmatter 记 modified，供判断新旧。

四、Cursor：主动放弃自动记忆 ​

Cursor 是三者里最激进的。据官方论坛工作人员回复，chat Memories 自 2.1.x 起被有意移除。官方给出的理由是：Memories 与 .mdc 规则差别不大。

于是记忆被拆成两件事：稳定约定归 rules（人写、可评审、可进 git），历史信息归检索（本地索引、按需命中）。产品不再判断"哪句话值得长期记住"。

这是一次收缩，也是一次取舍。代价是没有"用久了它自己懂你"的体验；收益是不会被过期记忆带偏。

它的规则体系反而因此更细：项目规则进 git，User Rules 随账号同步，Team Rules 后台下发且可强制，冲突时优先级为 Team > Project > User。代码检索走本地 Instant Grep，对话检索给历史 agent 转写建本地索引，并已作为 agent 可主动调用的工具。AGENTS.md 和 CLAUDE.md 也能被读取。

五、共同的取舍，比差异更值得记 ​

三家在细节上分歧很大，但底层判断高度一致：

第一，常驻内容必须小。 Codex 只注入摘要，Claude Code 只读 200 行，Cursor 只挂条件规则。没有一家把完整记忆灌进上下文。

第二，读取必须延迟。 细节不预先加载，等模型真的需要再去打开文件或搜索。这是把固定成本换成按需成本。

第三，写入必须做减法。 这是最容易被忽略的一条。Claude Code 排除代码可推导内容，Codex 用"30 天未使用"做被动剪枝，Cursor 干脆把判断权收回给人。

差异的根源是对"什么值得记"的信任度不同。Claude Code 信任模型判断，但给它立了明确的排除规则；Codex 信任后台模型，用时间与额度做被动裁剪；Cursor 不信任自动判断，只保留可审计的规则。

六、这对自建记忆系统意味着什么 ​

如果你在搭自己的 AI 记忆层，这三家的做法能反推出一条原则：

先设计"不记什么"，再设计"记什么"。

具体到操作：

  1. 把可推导的内容排除在外。 代码里能查到的、git 里能查到的，不要写成记忆。它们会过期，而且检索比记忆更准。
  2. 常驻层只放索引。 一行一条，能定位到细节文件就够。索引的价值是"知道去哪找"，不是"记住全部"。
  3. 给记忆加时间戳和淘汰规则。 没有失效机制的记忆库，一定会被过期信息污染。
  4. 区分"人写的约定"与"模型写的观察"。 前者该进版本控制、可评审；后者该可丢弃、可重建。混在一起是大多数自建方案的第一个错误。

不确定性与边界 ​

  • Cursor 的 chat Memories 已被移除。任何"Cursor 会自动记住你的偏好"的说法，都要按版本核对。
  • Codex 的具体召回算法（是否对记忆文件做 grep）官方未文档化，社区说法属二手，本文不采信为结论。
  • 三家都在快速迭代，本文结论以 2026-11-09 访问的官方文档为准。
  • 本文只覆盖官方文档描述的行为，不含第三方记忆插件与自建方案。

分厂商的细节见 Codex 的记忆系统、Claude Code 的记忆系统、Cursor 的记忆系统。
