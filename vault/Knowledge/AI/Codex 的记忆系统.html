Codex 的记忆分两层，但第一层根本不是记忆 ​

把 Codex 的 AGENTS.md 和 Memories 说成"两层记忆"，容易让人以为它们是一回事，只是层级不同。实际不是。

AGENTS.md 是指令链，由人写、进版本控制；Memories 是自动沉淀层，由后台模型写。 两者的生命周期、可信度、失效方式完全不同。混为一谈，会导致你在该用规则的地方用记忆，或者反过来。

一、第一层：AGENTS.md 是启动时拼出来的指令 ​

发现顺序是固定的：全局目录取一个文件（AGENTS.override.md 优先），然后从项目根逐级走到当前工作目录，每个目录最多取一个文件。拼接顺序是根在前、cwd 在后。

越靠近 cwd 的规则，实际优先级越高——不是因为官方规定了优先级，而是因为它出现在拼接结果的后面。这是个容易忽略的隐式规则。

兼容性方面，project_doc_fallback_filenames 可以把 CLAUDE.md 之类的文件当作指令文件读取。

大小限制是硬性的：合并后受 project_doc_max_bytes 限制，默认 32 KiB，超出部分不再加入。这意味着你把指令写得再详细，超过阈值也不会生效。

这层的特点是完全可审计。它是文件，能被 git 记录，能 code review，能回滚。出问题时你能确切知道是哪一行规则导致的。

二、第二层：Memories 是异步编译出来的 ​

第二层把记录拆成两段：单会话抽取，跨会话合并。两段可以分别指定模型，extract_model 负责前者，consolidation_model 负责后者。

产物是 Markdown 文件，下次会话只注入摘要层。

然后是整套门控设计，这是最值得看的部分：

机制行为
默认状态关闭，需要显式开启
会话筛选跳过活跃或短命的会话
时间门控会话结束不立即处理，默认空闲 6 小时后才进入候选
额度门控剩余额度低于阈值时跳过后台生成，默认 25%
合并上限参与合并的原始记忆默认 256 条，可调到 4096
时间剪枝30 天未被使用的记忆不再参与合并
会话年龄超过 30 天的会话不再参与生成
单次处理量每次启动最多处理 16 条
隐私生成字段做密钥脱敏；MCP 与联网会话可选择排除

读一遍这张表，你会发现没有一条在增加记忆。

默认关闭、跳过短命会话、空闲才处理、额度不足就停、参与合并有上限、30 天剪枝、单次最多 16 条——每一条都在限制它记事。

这不是设计失误。它的目标很明确：省额度、防污染。 空闲门控避免总结尚未完成的工作，配额门控避免后台任务抢占前台额度，时间剪枝控制无限膨胀。

三、召回机制没有公开 ​

这是最需要澄清的一点：官方文档只承诺"把已有记忆注入未来会话"，没有描述向量索引或相似度检索。

社区有说法称 Codex 对 MEMORY.md 做 grep，但那是二手推测，不是官方机制。把"grep 记忆文件"写成官方行为，是这类文章最常见的错误。

我在本机（2026-11-09）看过 memories/ 目录，见到 memory_summary.md、MEMORY.md、raw_memories.md、rollout_summaries/、extensions/ad_hoc/ 这些文件。但这是生成态，版本之间可能变化，不能当作官方契约。

四、真正的结论 ​

第一层是人与模型之间的契约，第二层是模型与自己的对话。

第一层你要认真写，因为它是唯一能精确控制行为的部分。它的失效方式是被 32 KiB 截断——所以规则要短、要靠近 cwd 生效。

第二层你不能精确控制，只能设边界：什么时候生成、什么时候不许生成、保留多久、合并多少。它的失效方式是过期信息污染——所以要有时间剪枝。

如果你的自建系统把这两件事混在一起，会同时失去两种保障：规则不再可审计，记忆不再可淘汰。

不确定性与边界 ​

  • 具体文件名与目录结构属生成态，v1/v2 迁移期间可能双写，升级后需重新核对。
  • "摘要之外如何取细节"官方未文档化；社区分析称对 MEMORY.md 执行 grep，属二手说法。
  • 地区可用性、默认开关状态可能随版本调整。
  • 本文以 2026-11-09 访问的 OpenAI 官方 Codex 文档为准。

总览见 三大编码 Agent 都没有记忆库，对照见 Claude Code 的记忆系统、Cursor 的记忆系统。
